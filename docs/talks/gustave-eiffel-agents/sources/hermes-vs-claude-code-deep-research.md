# Hermes Agent (Nous Research) vs. Claude Code: How the Mechanisms Actually Work

## TL;DR
- **Hermes is an open-source (MIT), model-agnostic, server-resident *personal* agent whose defining mechanism is a "closed learning loop": it autonomously writes reusable skill files from experience, patches them during use, nudges itself to persist memory, and searches its own past sessions — so it gets more capable the longer it runs.** Claude Code is a closed-source, Claude-tied *coding* CLI whose design philosophy is deliberate simplicity (one single-threaded loop, flat message history) and which does not autonomously author or refine its own skills.
- The biggest genuine architectural differences are: (1) **self-improvement** — Hermes has an in-loop skill-creation/refinement system plus a background "Curator" that ages and consolidates agent-written skills, which Claude Code has no equivalent of; (2) **memory** — Hermes uses bounded, agent-curated `MEMORY.md`/`USER.md` snapshots PLUS FTS5 session search PLUS optional external providers (Honcho dialectic user modeling), whereas Claude Code uses human-written `CLAUDE.md` plus "auto memory" notes and server-side compaction; (3) **openness/model** — Hermes runs on any provider (its own open-weight Hermes models, OpenRouter, OpenAI, local), Claude Code runs only on Anthropic's Claude models.
- For a presentation, the cleanest framing is **"depth of learning vs. controllable simplicity."** Hermes optimizes for a persistent agent that accumulates a personalized skill/memory corpus across many surfaces (CLI + 20 messaging platforms); Claude Code optimizes for a transparent, auditable, reliable coding agent in the terminal/IDE. Both now share the same open `SKILL.md` format and progressive-disclosure idea.

## Key Findings

1. **Hermes's core differentiator is a documented, in-product learning loop**, not just marketing. Four moving parts: (a) autonomous skill creation after complex tasks, (b) skill self-improvement (patching) during use, (c) periodic memory "nudges," and (d) cross-session FTS5 search. The GitHub README states it is "the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions."

2. **Memory is deliberately bounded and agent-curated, optimized for prompt caching.** Two files — `MEMORY.md` (agent notes, ~2,200 char limit / ~800 tokens) and `USER.md` (user profile, ~1,375 char / ~500 tokens) — are injected as a *frozen snapshot* into the system prompt at session start. Mid-session writes go to disk immediately but don't change the in-prompt copy until the next session, preserving the prefix cache. This is a distinct philosophy from Claude Code's CLAUDE.md (which is re-read from disk and re-injected after compaction).

3. **Skill creation is nudge-driven and condition-based.** Official docs say the agent creates a skill "After completing a complex task (5+ tool calls) successfully," when it found a working path through errors, when corrected, or when it discovered a non-trivial workflow. A config key `skills.creation_nudge_interval` (default 15) reminds the model every 15 tool-calling iterations to consider saving a skill. The widely-repeated third-party claim of a "reflection cycle every 15 tasks" is a misstatement of this config value (it is tool-calling iterations, not tasks, and it is a reminder, not a forced performance review).

4. **Self-improvement happens at two levels: in-session and offline.** In-session, the agent patches/edits the existing `SKILL.md` via the `skill_manage` tool when a procedure is outdated/incomplete/wrong. Separately, a companion repo `hermes-agent-self-evolution` uses DSPy + GEPA (Genetic-Pareto Prompt Evolution) to evolve skills, tool descriptions, and prompts offline via API calls and propose them as PRs — explicitly "not part of" the core agent.

5. **A background "Curator" prevents skill sprawl** — a genuinely novel mechanism with no Claude Code equivalent. It tracks usage telemetry, ages agent-created skills `active → stale (30d) → archived (90d)`, and runs an LLM review pass to consolidate near-duplicates. It never touches bundled or hub skills, never auto-deletes (archives only), and snapshots the skills tree before each run.

6. **Hermes is model-agnostic; Claude Code is Claude-only.** Hermes resolves three API modes (`chat_completions`, `codex_responses`, `anthropic_messages`) and, per the official README, lets you "Use any model you want — Nous Portal, OpenRouter (200+ models)… NVIDIA NIM (Nemotron), Xiaomi MiMo, z.ai/GLM, Kimi/Moonshot, MiniMax, Hugging Face, OpenAI, or your own endpoint. Switch with `hermes model` — no code changes, no lock-in." Claude Code runs exclusively on Anthropic Claude models (Opus/Sonnet/Haiku), switchable only among Claude variants.

7. **Both use the same open `SKILL.md` standard and progressive disclosure.** Anthropic published the Agent Skills specification on December 18, 2025 (at agentskills.io); within 48 hours Microsoft integrated it into VS Code and OpenAI added it to ChatGPT and Codex CLI. Hermes is compatible with that standard and can even install from `anthropics/skills` and Claude marketplace-style repos. So the *format* converged even as the *autonomy* diverged.

## Details

### A. Architecture at a glance

**Hermes.** A single platform-agnostic `AIAgent` class (`run_agent.py`, ~15k lines) serves every entry point: interactive CLI/TUI, a messaging **gateway** (20 platform adapters — Telegram, Discord, Slack, WhatsApp, Signal, Email, etc.), an ACP adapter for IDEs (VS Code/Zed/JetBrains), a batch runner, and an API server. The agent loop assembles a layered system prompt, resolves a provider/API-mode, makes interruptible model calls, dispatches tools (70+ tools across ~28 toolsets, single tools in the main thread and multiple via a thread pool), compresses context, and persists to SQLite. Design principles it states explicitly: prompt stability (no cache-breaking mid-conversation), observable execution, interruptibility, platform-agnostic core, loose coupling, and profile isolation. It is built by model trainers (Nous Research, the lab behind the Hermes open-weight models, Nomos, and Psyche).

**Claude Code.** Per multiple source-level analyses (including the arXiv study "Dive into Claude Code," arXiv:2604.14228, by Liu, Zhao, Shang and Shen, which analyzed the publicly-available v2.1.88 TypeScript source), the core is a single-threaded master loop (community-codenamed "nO") — a `while(tool_calls)` loop with one flat, append-only message history, chosen deliberately for debuggability and reliability over multi-agent "swarms." That paper documents "a permission system with seven modes and an ML-based classifier, a five-layer compaction pipeline… Up to 54 built-in tools (19 unconditional, 35 conditional)," plus controlled sub-agents (at most one branch deep, no recursive spawning). Note: the "nO"/"h2A" codenames and the ~512K-line source figure come from third-party reverse-engineering and a source-map leak (March 31, 2026), not official Anthropic docs — they are widely corroborated but should be flagged as secondary.

The deepest architectural contrast: **Hermes embraces first-class isolated sub-agents and a multi-surface persistent gateway; Claude Code embraces a single auditable loop in a developer context.** The arXiv comparison frames the same recurring design questions producing different answers under different deployment contexts.

### B. Memory — the deep topic

**Hermes memory has up to five layers:**

1. **`MEMORY.md`** — agent's personal notes (environment facts, conventions, lessons), ~2,200 chars / ~800 tokens.
2. **`USER.md`** — user profile (identity, preferences, communication style), ~1,375 chars / ~500 tokens.
   - Both live in `~/.hermes/memories/`, are injected as a **frozen snapshot** at session start, and are managed by the agent via a `memory` tool with `add`/`replace`/`remove` actions (substring matching, no `read` action because it's always in-prompt). When full, the tool errors and the agent must consolidate. Entries are security-scanned for injection/exfiltration patterns. The character caps are intentional: they keep the system prompt bounded and the prefix cache stable.
3. **Session search** — every CLI and messaging session is stored in SQLite (`~/.hermes/state.db`) with **FTS5 full-text search**; a `session_search` tool does discovery (~20ms), scroll (~1ms), and browse with **no LLM cost** at query time. This is "unlimited" episodic recall versus the tiny always-in-context memory.
4. **External memory providers (optional plugins)** — Hermes ships 8 provider plugins (Honcho, Mem0, Supermemory, etc.); only one active at a time, running *alongside* built-in memory. **Honcho** (Plastic Labs) is the flagship: it does "dialectic" user modeling — a peer-centric system where a background reasoner derives *conclusions/representations* rather than storing raw transcripts. As one third-party analysis (CrabTalk/openwalrus.xyz) puts it, Honcho derives "Theory of Mind snapshots… These aren't raw transcripts. They're conclusions: 'User has 10+ years Rust experience,' 'User prefers async communication.'" Queried in natural language; requires `HONCHO_API_KEY`; it's the only layer needing an external service.
5. **Periodic memory nudge** — the agent is reminded every N user turns (config `memory.nudge_interval`, default 10) to consider persisting anything durable, plus a `flush_min_turns` (default 6) that grants one save-turn before context is lost to compression/`/new`/`/reset`/exit.

**Context management / compaction.** Hermes has a **dual compression system** built on a pluggable `ContextEngine` ABC (default `ContextCompressor`; plugins can swap in lossless engines). The agent's own compressor fires at **50%** of context (configurable); a gateway "session hygiene" safety net fires at **85%**. Compression is a 4-phase algorithm: (1) prune old tool outputs >200 chars (no LLM), (2) determine boundaries protecting first 3 and last ~20 messages, keeping tool-call/result pairs intact, (3) generate a *structured* summary (Goal/Constraints/Progress/Decisions/Files/Next Steps/Critical Context) via an auxiliary LLM, (4) reassemble. Re-compression *updates* the prior summary rather than re-summarizing from scratch. Anthropic prompt caching uses a "system_and_3" strategy (system prompt + rolling 3-message window = the 4 allowed cache breakpoints), cutting input token cost by ~75% on multi-turn conversations.

**Claude Code memory.** Two complementary mechanisms loaded at the start of every session: (1) **`CLAUDE.md`** files — human-written persistent instructions, walked up the directory tree and additively merged (global `~/.claude`, project, local), treated as a "behavioral contract," practical cap ~150–200 instructions / ~80–200 lines before adherence degrades; (2) **auto memory** (added in Claude Code v2.1.59) — Claude writes its own markdown notes to `~/.claude/projects/<project>/memory/`, loading the first ~200 lines of a `MEMORY.md` at startup. Context is managed by **server-side compaction** (auto-summarization near the window limit, manual `/compact`), microcompact, and context editing (tool-result clearing). Crucially, **project-root `CLAUDE.md` survives compaction because it is re-read from disk and re-injected** — the opposite of Hermes's deliberately frozen snapshot. There is no built-in FTS5 cross-session search; third-party plugins (claude-mem, Honcho) fill that gap.

**The contrast in one line:** Hermes treats memory as an *agent-curated, bounded, multi-layer, searchable* system that the agent maintains autonomously; Claude Code treats memory as a *human-authored instruction file plus lightweight auto-notes*, re-injected deterministically, with retrieval/search left to plugins.

### C. Autoskill creation

- **Where skills live:** `~/.hermes/skills/`, one directory per skill, each with a `SKILL.md` (YAML frontmatter: `name`, `description`, `version`, optional `platforms`, `metadata.hermes.tags/category`) plus optional `references/`, `templates/`, `scripts/`, `assets/`. Compatible with the **agentskills.io** open standard. Skills surface as slash commands (`/skill-name`) and via a compact **progressive-disclosure** index (Level 0 list ~3k tokens → Level 1 full content → Level 2 reference file).
- **How the agent creates them:** via the `skill_manage` tool (`create`, `patch`, `edit`, `delete`, `write_file`, `remove_file`). This is the agent's **procedural memory**.
- **When:** "After completing a complex task (5+ tool calls) successfully," after finding a working path through errors/dead-ends, after a user correction, or after discovering a non-trivial workflow. A system-prompt guidance block plus the `skills.creation_nudge_interval` (default **15 tool-calling iterations**) reminds it to consider saving one.
- **Format stored:** markdown `SKILL.md` with structured sections (When to Use / Procedure / Pitfalls / Verification).

### D. Auto skill improvement / self-improvement

- **In-session refinement:** when a skill proves outdated/incomplete/wrong during reuse, the agent **patches the existing `SKILL.md`** in place (the `patch` action is preferred for token efficiency). No separate engine — same `skill_manage` write path. This is "skills self-improve during use."
- **Background Curator (maintenance loop):** triggered by an inactivity check (default every **168h / 7 days**, only after **2h idle**), it spawns a background fork of `AIAgent`. Phase 1 (deterministic): age skills `active → stale (30d) → archived (90d)`. Phase 2 (LLM review, max 8 iterations): survey agent-created skills, patch/consolidate/archive. It only touches **agent-created** skills (not bundled/hub), **never auto-deletes**, snapshots the skills tree (tar.gz) before each run, supports `--dry-run`, rollback, and pinning. Telemetry lives in `~/.hermes/skills/.usage.json` (use/view/patch counts).
- **Offline evolutionary self-improvement (separate repo):** `NousResearch/hermes-agent-self-evolution` uses **DSPy + GEPA** to read execution traces, mutate skills/tool-descriptions/prompts/code, evaluate variants behind constraint gates (tests, size limits), and raise PRs. ~$2–10 per run, no GPU. This is research infrastructure that operates *on* Hermes, not inside it.

**Claude Code has no analog to autonomous skill authoring or curation.** Its skills are human-authored (or built via plugins), and while subagents can keep their own auto-memory, the system does not write or refine its own `SKILL.md` library from task experience.

### E. Other notable mechanisms

- **Sub-agents / delegation.** `delegate_task` spawns isolated child `AIAgent` instances with fresh context (`skip_context_files=True`, `skip_memory=True`), their own terminal session and restricted toolsets; only the final summary returns to the parent ("zero-context-cost"). Up to 3 concurrent by default (`delegation.max_concurrent_children`), 50 iterations each, spawn depth 1 by default (raisable to 3 with orchestrator/leaf roles). Leaf subagents cannot call `delegate_task`, `clarify`, `memory`, `send_message`, or `execute_code`. *Contrast:* Claude Code also isolates sub-agents but limits to one branch deep with no recursion — a more conservative stance.
- **`execute_code` RPC.** The agent writes Python that calls Hermes tools via RPC, collapsing multi-step pipelines into a single LLM turn.
- **Execution environments / sandboxing.** Seven terminal backends — local, Docker, SSH, Singularity, Modal, Daytona, Vercel Sandbox — with container hardening (read-only root, dropped capabilities, PID limits, namespace isolation). Docker backend is one persistent container shared across the process. Modal/Daytona offer serverless hibernation. *Claude Code* runs tools in a local sandboxed environment tied to the dev machine/IDE.
- **Scheduling.** Built-in cron scheduler runs agent tasks (not shell tasks) in natural language and delivers to any platform.
- **Tool use & error recovery.** Three API modes converge on OpenAI-style messages; iteration budget default 90 turns; fallback model chain on 429/5xx/auth errors with credential refresh; interruptible API calls (abandon in-flight on new input). MCP supported for external tools.
- **Model coupling.** Hermes can run on the open-weight **Hermes 4** family (Llama-3.1-based, 70B/405B, hybrid `<think>` reasoning) but is explicitly *not* tied to it — it's model-agnostic. Claude Code is tied to Claude.

### F. Adoption / reputability context (secondary sources)

Multiple secondary outlets (TechTimes, NVIDIA's blog, DEV, kisztof.medium.com, others) report Hermes launched **February 25, 2026**; one review (kisztof.medium.com) states it "crossed 95,000 GitHub stars" seven weeks after launch and "sits around 105,000" at the time of writing, "making it the fastest-growing open-source agent framework of the year." Around **May 10, 2026** it reportedly overtook OpenClaw as the most-used agent on OpenRouter by daily token volume (~224B tokens/day vs 186B). These are usage/popularity claims from third-party trackers, not architecture facts, and should be presented as such. The GitHub repo page itself shows very large star/fork counts consistent with this.

## Recommendations

**For the presentation, structure it around three contrasts and lead with the learning loop.**

1. **Open with the one-slide thesis:** "Depth of learning (Hermes) vs. controllable simplicity (Claude Code)." Use the README quote ("the only agent with a built-in learning loop…") as the hook, then immediately show the closed-loop diagram: task → skill created → skill patched during use → memory nudge → session search feeds the next task.

2. **Spend the most time on memory and skills** (the user's stated deep topics). Show the concrete artifacts: the frozen `MEMORY.md` block with the `%`-capacity header, the `SKILL.md` skeleton, and the Curator state machine (`active → stale → archived`). Contrast each directly with the Claude Code equivalent (`CLAUDE.md` + auto memory + server-side compaction). The single sharpest technical contrast to feature: **Hermes freezes the memory snapshot to protect the cache; Claude Code re-reads `CLAUDE.md` from disk after every compaction.**

3. **Be precise about the "every 15" claim** — present it as `creation_nudge_interval: 15` *tool-calling iterations* (a reminder), and explicitly debunk the popular "reflection cycle every 15 tasks" phrasing as a third-party error. This earns credibility with a technical audience.

4. **Show the model/openness axis as a strategic point, not a feature bullet:** Hermes is MIT, self-hosted, runs on any model including local open-weights; Claude Code is closed and Claude-only. Tie this to *why* Hermes can afford an always-on, multi-surface persistent agent (cost control, local inference) while Claude Code optimizes a premium coding experience.

5. **If you demo, demo the divergence:** create a skill in Hermes by completing a multi-step task and show the `~/.hermes/skills/` file appear; then show Claude Code requiring a human-written `SKILL.md`. That single contrast makes the "self-improving" claim concrete.

**Benchmarks/thresholds that would change the recommendation:** if you need an auditable, single-threaded, production coding agent with enterprise permission controls in an IDE, Claude Code's simplicity is the better fit; if you need a persistent, multi-channel personal agent that accumulates a private skill/memory corpus and runs on your own/open models, Hermes is the better fit.

## Caveats

- **Source tiers.** Tier 1 (primary/official): the Hermes site, its docs (`hermes-agent.nousresearch.com/docs`), and the `NousResearch/hermes-agent` repo (README, `cli-config.yaml.example`, developer-guide pages) — these back essentially all Hermes mechanism claims here. Claude Code's official docs (code.claude.com, platform.claude.com) back the CLAUDE.md/auto-memory/compaction/model-config claims. Tier 2 (secondary, flagged inline): third-party blogs and the arXiv "Dive into Claude Code" study (arXiv:2604.14228) for Claude Code's internal loop codenames ("nO"/"h2A"), the ~512K-line figure, the seven-mode permission system / 54-tool count, and all adoption/popularity statistics. These are widely corroborated but are not official Anthropic statements.
- **The "every 15 tasks" figure is a third-party misstatement** of the official `creation_nudge_interval: 15` (tool-calling iterations). The config key and default were verified against the repo's `cli-config.yaml.example`; one retrieval of that file came via a public mirror due to rate-limiting, so confirm directly against the canonical repo URL if exact wording matters for the talk. Note also two *separate* nudges exist: skill-creation (`skills.creation_nudge_interval: 15` tool iterations) and memory (`memory.nudge_interval: 10` user turns) — blogs frequently conflate them.
- **"Self-improving" is partly aspirational.** Independent reviewers note the in-session loop amplifies whatever the base model does (a weak model writes weak skills) and that skills can proliferate without curation. The headline efficiency claim — that an agent using self-created skills "completed research tasks 40% faster than a fresh instance, with no prompt tuning" (NxCode, citing Nous Research's own benchmarks) — is a vendor/secondary figure, not independent evaluation. Treat efficacy claims as vendor/secondary, not established.
- **Version drift.** Hermes is pre-1.0 and shipping extremely fast (multiple releases/month; the site showed v0.15.2 and the repo showed v0.14.0 / v2026.5.x tags at research time), and Claude Code updates frequently too; specific numbers (thresholds, backend counts, platform counts) may change between your research date and the talk.
- **Honcho efficacy is unproven for Hermes specifically.** Plastic Labs reports strong memory-benchmark numbers (e.g., 90.4% on LongMem-S, 89.9% on LoCoMo at a median 5% of context — per evals.honcho.dev via dev.to), but there is no Hermes-specific A/B evidence that dialectic user modeling measurably improves task performance (as openwalrus.xyz notes, the "understands you better over time" value proposition "needs evidence… anything quantitative"). Present it as a capability, not a proven win.
