# Memory in Agent Harnesses: Conceptual Layers, Shared Problems, and Where Claude Code and Hermes Agent Land

## TL;DR
- **Every agent memory system is really solving one problem in different costumes:** the LLM context window is finite, degrades over length ("context rot"), and is wiped between sessions — so all harnesses layer working memory (context window), externalized scratchpads/notes files, persistent cross-session stores, and retrieval over them. Claude Code and Hermes Agent both implement this same stack but make opposite bets on *who controls memory* and *how much is automated*.
- **Claude Code** bets on context engineering primitives: CLAUDE.md instruction files loaded at startup, server-side compaction near the context limit, tool-result clearing, sub-agents with isolated context, a file-based `/memories` memory tool, and auto memory — i.e., the model curates lightweight notes while Anthropic's harness manages the window. **Hermes Agent (Nous Research)** bets on a tightly bounded, agent-curated memory (MEMORY.md ~2,200 chars + USER.md ~1,375 chars), a pre-compaction "memory flush," unlimited FTS5 session search, procedural memory as self-authored *skills*, a weekly Curator, and 8 pluggable external memory providers.
- **The field (April–May 2026) is converging on "memory as a learned, evolving, governed process"** — self-editing playbooks (ACE), RL-trained memory operations, sleep-time/"dreaming" consolidation, graph- and connectivity-based memory, and a fast-emerging memory *security/governance* subfield (poisoning, exfiltration, "mnemonic sovereignty"). Open problems: continual consolidation, learned forgetting that doesn't delete safety-critical info, causally-grounded retrieval, and evaluation.

---

## Key Findings

1. **There is a canonical taxonomy, and it is borrowed from cognitive science.** The CoALA framework (Cognitive Architectures for Language Agents, Princeton/CMU, arXiv:2309.02427, 2023) adapted Tulving's human-memory categories into four agent memory types — working/in-context, episodic, semantic, procedural — and essentially every major framework (Letta, Mem0, LangGraph, IBM, MongoDB) now builds on it. A 2026 wave of surveys refines this into a *write–manage–read* lifecycle.

2. **The shared foundation is the finite, degrading, amnesiac context window.** Anthropic itself frames context as "a finite resource with diminishing marginal returns" and cites "context rot." The underlying empirical work — Kelly Hong, Anton Troynikov & Jeff Huber, "Context Rot: How Increasing Input Tokens Impacts LLM Performance" (Chroma technical report, July 2025), which evaluated 18 LLMs including GPT-4.1, Claude 4, Gemini 2.5 and Qwen3 — found that "models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows," with needle-in-a-haystack-style accuracy dropping 20–50% from 10k to 100k+ tokens. Transformer attention is n² in tokens, so longer context = more diffuse attention. Every memory architecture exists to move information *out of* and *back into* this scarce window intelligently.

3. **Claude Code and Hermes Agent implement the same conceptual layers but with opposite philosophies.** Claude Code = harness-managed context engineering with lightweight model-curated notes; Hermes = agent-as-owner of a bounded curated memory plus a learning loop that converts experience into reusable skills (procedural memory).

4. **The cutting edge is "memory management as a skill the system learns or evolves," not a fixed pipeline.** ACE's "evolving playbooks," Letta's sleep-time compute ("dreaming"), RL-trained memory operations (Memory-R1, Agentic Memory, MemRL), and graph/connectivity memory (FluxMem, MAGMA) are all 2025–2026 directions. A parallel memory-*security* field exploded in May 2026.

## Details

### 1. Conceptual overview of memory layers — what each is and why it exists

**Working memory / context window (in-context memory).** This is the live token buffer the model attends to on each forward pass — system prompt, tools, message history, retrieved data, the model's own reasoning. It is the only memory the model "natively" has; everything else is machinery to feed this window. It exists because the model is otherwise stateless: between API calls it remembers nothing. Its defining constraint is that it is finite and, per Anthropic, suffers diminishing returns well before the hard token limit because of "context rot" — recall accuracy drops as tokens grow.

**Short-term vs. long-term memory.** Short-term ≈ the current session/context window; long-term = anything persisted outside it (files, databases, vector stores) that survives session boundaries. The conceptual reason to separate them is that they have different cost, latency, and durability profiles: short-term is instantly available but expensive (every token is re-billed and dilutes attention); long-term is cheap to hold but must be *retrieved* to be useful.

**Episodic vs. semantic vs. procedural (the three long-term stores).**
- *Episodic memory* stores specific past events/interactions with temporal context ("on 2026-01-15 we migrated MySQL→PostgreSQL"; CoALA: "experience from earlier decision cycles"). It is written by logging and read during planning for analogical reasoning.
- *Semantic memory* stores generalized facts and knowledge abstracted from episodes ("the user prefers TypeScript"; "Paris is the capital of France"). The transformation from episodic → semantic is called *consolidation*.
- *Procedural memory* stores skills/how-to — rules, scripts, reusable workflows ("how to debug a CrashLoopBackOff pod"). In agents this often manifests as system-prompt logic or, increasingly, self-authored skill files.
Together these form a "reasoning stack": procedure says *how*, semantic says *what's true*, episodic says *what happened*, working memory holds the live reasoning.

**Scratchpads / notes files (CLAUDE.md, MEMORY.md, todo.md, NOTES.md).** These are the simplest and most-used externalization: the agent (or human) writes plain-text/markdown notes to disk that get loaded back into context. Anthropic calls this "structured note-taking" or "agentic memory." Yichao 'Peak' Ji (Co-Founder and Chief Scientist of Manus AI), in "Context Engineering for AI Agents: Lessons from Building Manus" (July 18, 2025), wrote that "we treat the file system as the ultimate context in Manus: unlimited in size, persistent by nature, and directly operable by the agent itself." The conceptual mechanism: offload high-value state to a durable file, keep only a pointer or summary in context, re-read on demand. The Manus *todo.md*-recitation trick also exploits this to fight "lost-in-the-middle" by re-appending goals to the end of context.

**External memory stores (vector databases, knowledge graphs).** When persisted knowledge grows beyond what any file can hold, agents use structured backends: vector DBs for semantic similarity search over embeddings; knowledge graphs for entities and relationships; SQL/FTS for exact text search. The reason: scalable, queryable recall that doesn't fit in context. Graph-based memory (2025–2026 frontier) preserves *how* facts connect over time rather than treating memory as a flat log.

**Retrieval-augmented memory (RAG) and "just-in-time" retrieval.** Rather than pre-loading everything, the agent fetches relevant context at runtime. Two styles: *pre-inference embedding retrieval* (classic RAG) and Anthropic's preferred *just-in-time* approach where the agent holds lightweight identifiers (file paths, queries, links) and loads data on demand using tools (glob, grep, Bash). The reason: relevance and token economy — load only what the current step needs.

**Context compaction / summarization.** When the window nears its limit, the conversation is summarized and the window reinitialized with the summary. Anthropic's Claude Code passes message history to the model to "summarize and compress the most critical details… preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," then continues with the summary plus the five most recently accessed files. The reason: extend effective horizon without exhausting tokens. The risk: lossy summarization can drop a critical file path or error.

**Session-persistent memory.** State that deliberately bridges sessions — Claude Code's CLAUDE.md (re-read after compaction) and `/memories` tool; Hermes's MEMORY.md/USER.md and SQLite session DB. The reason: each new session starts with a fresh window, so without explicit persistence the agent has "digital amnesia."

### 2. Common ground — the problems EVERY agent memory system must solve

Regardless of solution, these problems recur (synthesized from Anthropic's context-engineering posts and the 2026 surveys arXiv:2603.07670, 2512.13564, 2605.06716):

1. **Finite context window.** Hard token cap; most non-trivial tasks exceed it. → compaction, offloading, retrieval.
2. **Context rot / degradation over long horizons.** Even within limits, recall and long-range reasoning degrade as tokens grow (n² attention; training skew toward short sequences). "Long context is not memory." → keep the window small and high-signal.
3. **Cross-session persistence.** Each session starts blank ("engineers working in shifts with no memory of the previous shift," per Anthropic). → durable files/DBs, handoff artifacts.
4. **Retrieval relevance.** Stored ≠ accessible; the system must surface the *right* memory at the right time. → embeddings, reranking, graphs, agent-controlled search.
5. **Write-path filtering (what to remember).** Storing everything poisons recall and inflates cost. → importance heuristics, dedup, "save vs skip" rules.
6. **Forgetting / eviction.** Memory must be bounded; something must be dropped or archived. → capacity limits, staleness/archival, learned forgetting (risky — may delete safety-critical info).
7. **Consistency / contradiction handling.** New facts contradict old ones; memory must revise, not just append. → consolidation, conflict detection.
8. **Cost & latency of large contexts.** Tokens cost money and time; KV-cache hit rate is, per Manus, "the single most important metric for a production agent." → caching, append-only designs, offloading.
9. **Memory consolidation.** Turning raw episodes into durable, generalized knowledge. → reflection, summarization, sleep-time passes.
10. **(Newly prominent, 2026) Governance & security.** Memory is an attack surface (poisoning, exfiltration) and a privacy/audit concern.

**How the two systems approach these shared problems:**

| Shared problem | Claude Code's choice | Hermes Agent's choice |
|---|---|---|
| Finite window | Server-side compaction near limit + tool-result clearing | Agent ContextCompressor at 50% of context; gateway safety net at 85% |
| Cross-session persistence | CLAUDE.md (re-read after compaction) + `/memories` file tool + auto memory | Bounded MEMORY.md/USER.md injected at session start + SQLite session DB |
| What to remember | Model writes notes from corrections/preferences; CLAUDE.md curated by humans | Strict char limits force consolidation; explicit "save vs skip" rules; pre-compaction "memory flush" |
| Retrieval | Just-in-time (glob/grep/Bash, file paths) + hybrid pre-load of CLAUDE.md | FTS5 full-text session search (~20ms, no LLM) + optional vector/graph providers |
| Forgetting/eviction | Compaction discards redundant tool output; `/clear` resets | Char-limit-driven replace/consolidate; weekly Curator archives stale skills |
| Long-horizon coherence | Sub-agents with clean context; structured note-taking; harness with feature-list + progress file | Contained sub-agents; skills as procedural memory; cron + persistent runtime |

### 3. Solution specifics

#### Claude Code (Anthropic)

Claude Code's memory model is the practical embodiment of Anthropic's **"Effective context engineering for AI agents"** (Sep 29, 2025) and **"Effective harnesses for long-running agents"** (Nov 26, 2025), plus the **"Harness Design for Long-Running Application Development"** work (Mar 2026, a three-agent planning/generation/evaluation harness).

- **CLAUDE.md memory files.** Markdown instruction files loaded into context at the start of *every* session. Anthropic's docs: target under 200 lines; use path-scoped rules and imports for organization. They're treated as *context, not enforced configuration* (use a PreToolUse hook to truly block actions). Crucially, **project-root CLAUDE.md survives compaction** — after `/compact`, Claude re-reads it from disk. Loading order walks up the directory tree, additively. This is *semantic + procedural* memory, human-curated.
- **Auto memory.** Claude writes its own notes from your corrections and preferences; subagents can maintain their own auto memory. This is the model-curated complement to human-written CLAUDE.md.
- **Compaction.** Server-side summarization (beta header `compact-2026-01-12`; strategy `compact_20260112`) that fires near the context limit (community reports ~95%; Claude Code default window 200K, up to 1M for Opus/Sonnet 4.x via beta header at premium rates). It detects threshold, generates a summary, emits a compaction block, and drops prior messages. Known failure: summaries can drop file paths/error codes — hence the advice to put durable rules in CLAUDE.md and compact manually at task boundaries.
- **The memory tool (`/memories`).** A client-side, file-based store (create/read/update/delete in a `/memories` directory) that persists across conversations and is eligible for Zero Data Retention. It's "the key primitive for just-in-time context retrieval": Claude checks memory before tasks, writes what it learns, and recovers project state in seconds in later sessions. Pairs with context editing (clears tool results client-side) and compaction (server-side summarization).
- **Context editing / tool-result clearing.** The "safest, lightest-touch" compaction: once a tool result is deep in history, clear it.
- **Sub-agent architectures.** Specialized sub-agents each get an isolated context window (Task tool ≈ own 200K), explore using tens of thousands of tokens, and return a distilled ~1,000–2,000-token summary to the lead agent. Separation of concerns keeps the orchestrator's context clean.
- **Long-running harness.** An *initializer agent* sets up the environment once (an `init.sh`, a `claude-progress.txt` log, a git repo, and a JSON feature-list of ~200+ end-to-end features marked "failing"); a *coding agent* makes incremental progress one feature at a time, self-verifies with browser automation (Puppeteer MCP), commits to git, and updates the progress file. This is episodic/procedural memory externalized to the filesystem to bridge the cross-session amnesia gap.

In short, Claude Code's bet: keep the model's window lean via harness-side context engineering, persist a little (CLAUDE.md + /memories + progress files), and let just-in-time retrieval pull the rest.

#### Hermes Agent (Nous Research)

Hermes Agent (open-source, MIT, released Feb 25, 2026; one of the fastest-growing agent frameworks of 2026 by GitHub stars) is built around a **closed learning loop** and treats memory as a **layered, agent-owned** system. The current release line is v0.14.0 (May 16, 2026).

- **Built-in persistent memory: MEMORY.md + USER.md.** Two deliberately *bounded* files in `~/.hermes/memories/`: **MEMORY.md** (agent's personal notes — environment facts, conventions, lessons; limit **2,200 chars / ~800 tokens**) and **USER.md** (user profile — preferences, communication style; limit **1,375 chars / ~500 tokens**). They're injected into the system prompt as a **frozen snapshot at session start** (deliberate, to preserve the prefix cache); mid-session writes persist to disk but don't re-appear until next session. The agent manages them via a `memory` tool with **add / replace / remove** actions (no `read` — it's already in context). Entries are `§`-delimited, usage % is shown so the agent knows capacity, and at >80% it's told to consolidate. Hard char limits *force* consolidation/eviction — a striking contrast to unbounded vector stores. Entries are also security-scanned for injection/exfiltration patterns before acceptance.
- **Pre-compaction "memory flush."** Hermes uses a **dual compression system**: the in-loop Agent ContextCompressor triggers at **50% of context** (default `threshold: 0.50`, `target_ratio: 0.20`, `protect_last_n: 20`, `protect_first_n: 3`), and a gateway "session hygiene" safety net at a fixed **85%** of context. Critically, *before* context is discarded, **"memory is flushed to disk first"** — the agent is given **one extra turn to call the `memory` tool and persist info to MEMORY.md/USER.md** before compression, `/new`, `/reset`, or exit. On exit/reset the flush only fires if the session had at least `flush_min_turns` (default **6**) user turns. This directly targets the "lossy summarization drops critical info" problem.
- **Session search (episodic recall).** All CLI and messaging sessions are stored in SQLite (`~/.hermes/state.db`) with **FTS5 full-text search**; the `session_search` tool returns actual past messages (no LLM summarization, no truncation) in ~20ms, with ~1ms scroll. Unlimited capacity, free (no LLM calls), used on demand — the complement to the always-in-context bounded memory.
- **Skills = procedural memory (the self-improvement loop).** After completing a **complex task (5+ tool calls)** successfully — or after recovering from errors, being corrected, or discovering a non-trivial workflow — the agent can autonomously author a `SKILL.md` (YAML frontmatter + procedure/pitfalls/verification) via the **`skill_manage`** tool (actions: create, patch, edit, delete, write_file, remove_file). Skills live in `~/.hermes/skills/`, follow the agentskills.io open standard, and use **progressive disclosure** (Level 0 list ~3k tokens → Level 1 view → Level 2 sub-file). This is "remembering methods, not just facts." *(Note: several secondary blogs claim a "self-evaluation checkpoint every 15 tool calls"; this number does NOT appear in any Nous primary source. The documented mechanism is a rubric-based background "review fork" that runs after each turn — restricted to memory + skills toolsets — plus "periodic nudges," with no published numeric interval.)*
- **Curator (skill consolidation / forgetting).** A background maintenance pass on a **7-day default cycle** (`interval_hours: 168`, runs only after `min_idle_hours: 2` idle) that tracks skill usage telemetry, moves agent-created skills `active → stale (30d) → archived (90d)`, and runs an LLM review to consolidate near-duplicates. It never touches bundled/hub skills, never auto-deletes (archives are recoverable), takes tar.gz snapshots before each run, and supports pin/rollback. This is *learned forgetting with safety rails*.
- **8 pluggable external memory providers.** Beyond the built-ins, exactly one external provider can be active alongside built-in memory: **Honcho** (dialectic cross-session user modeling), **Mem0** (server-side LLM fact extraction), **Hindsight** (knowledge graph + cross-memory "reflect" synthesis), **OpenViking** (filesystem hierarchy + tiered L0/L1/L2 loading), **Holographic** (local SQLite + FTS5 + HRR algebra + trust scoring), **RetainDB** (hybrid vector+BM25+rerank, delta compression), **ByteRover** (knowledge tree with pre-compression extraction), and **Supermemory** (semantic recall + context fencing). When active, Hermes auto-injects provider context, prefetches before each turn, syncs turns after responses, and extracts on session end.

In short, Hermes's bet: give the *agent* ownership of a small, high-signal, security-scanned memory; never silently lose it (flush before compaction); make episodic recall unlimited and cheap via FTS5; and turn experience into reusable procedural skills that a Curator keeps tidy.

### 4. Where the field is going + open problems (recency-focused, April–May 2026)

**The throughline: memory as a learned, evolving, governed process — not a static store.** Recent surveys (arXiv:2603.07670 "Memory for Autonomous LLM Agents," Mar 2026; arXiv:2512.13564 "Memory in the Age of AI Agents," Dec 2025/Jan 2026; arXiv:2605.06716 "From Storage to Experience," May 7, 2026) all frame an evolution from *storage → reflection → experience* and a *write–manage–read* loop with learned control.

Concrete recent directions and primary sources:

- **Self-editing / evolving-context memory.** *Agentic Context Engineering (ACE)* (Zhang, Hu, Upasani et al., arXiv:2510.04618; v1 Oct 6, 2025; v3 Mar 29, 2026) treats context as an "evolving playbook" updated by a generator/reflector/curator loop with "grow-and-refine" incremental updates, explicitly to prevent **"context collapse"** (iterative rewriting eroding detail) and **"brevity bias."** It reports "+10.6% on agents and +8.6% on finance"; ReAct+ACE reached 59.5% average on AppWorld, matching IBM's GPT-4.1 CUGA agent on the Sept 20, 2025 leaderboard despite using a smaller open-source model. This is essentially "memory management as a first-class skill."
- **Learned (RL-trained) memory operations.** *Memory-R1* trains sub-agents to decide add/update/delete via RL; *Agentic Memory* (Yu et al., 2026) trains store/retrieve/update/summarize/discard as tools via three-stage GRPO and discovers non-obvious strategies like preemptive summarization; *MemRL* (Jan 2026) does runtime RL on episodic memory; *Memex(RL)* (arXiv:2603.04257) scales long-horizon agents via indexed experience memory with smaller working context.
- **Sleep-time compute / "dreaming" (consolidation during idle time).** Letta (formerly MemGPT) offloads memory reorganization to a background "sleep-time" agent during idle turns — consolidating archival items, rewriting messy memory blocks — now rebranded "dreaming." This operationalizes consolidation as asynchronous housekeeping. Letta Code (memory-first coding agent) extends the OS-inspired core/archival/recall tiering ("LLM OS," virtual vs. physical context).
- **Memory-as-OS / structured long-horizon systems.** *EverMemOS* (Jan 2026, "self-organizing memory operating system"), and the broader MemGPT/Letta "LLM OS" lineage.
- **Graph- and connectivity-based memory.** *Graph-based Agent Memory* survey (arXiv:2602.05665) calls graphs "the frontier for 2025–2026"; *MAGMA* (multi-graph agentic memory, Jan 2026); *FluxMem* "Rethinking Memory as Continuously Evolving Connectivity" (arXiv:2605.28773, May 27, 2026) — repairs links, prunes interference, distills recurrent successful trajectories into reusable procedural circuits; SOTA on LoCoMo/Mind2Web/GAIA. *H-Mem* (arXiv:2605.15701, May 15, 2026) models memory evolution with a hybrid structure.
- **Memory security & governance — a fast-emerging subfield (heavily May 2026).** *Trojan Hippo: Weaponizing Agent Memory for Data Exfiltration* (arXiv:2605.01970, May 3, 2026); *What Happens Inside Agent Memory? Circuit Analysis* (arXiv:2605.03354, May 5, 2026) — finds control circuitry is active at 0.6B but content circuitry only at 4B, exposing a regime where small models route memory decisions before they can reliably ground facts; *Is Agent Memory a Database?* (arXiv:2605.26252, May 25, 2026) proposes "Governed Evolving Memory (GEM)" with state-level operators; a *Survey on the Security of Long-Term Memory* (arXiv:2604.16548) coins **"mnemonic sovereignty."** A May 2026 industry roundup (mem0's "State of AI Agent Memory 2026") and the "Memory Wall" commentary mark this as an inflection point. The SSGM framework (arXiv:2603.11768) names three failure points: memory poisoning (ingestion), semantic drift (consolidation), and conflict/hallucination (retrieval).
- **Benchmarks & evaluation gaps.** Surveys note benchmark saturation, metric misalignment (F1 vs. semantic correctness), prompt sensitivity in LLM-as-judge, and the shift from static recall benchmarks to multi-session agentic tests (MemoryArena, LoCoMo). The first broad head-to-head was Chhikara, Khant, Aryan, Singh & Yadav, "Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory" (ECAI 2025, arXiv:2504.19413), which on LOCOMO reported that "Mem0 achieves 26% relative improvements in the LLM-as-a-Judge metric over OpenAI," with "91% lower p95 latency" and "more than 90%" token-cost savings versus full-context. Mem0's April 2026 token-efficient algorithm ("State of AI Agent Memory 2026," mem0.ai) claims "+29.6 points" on temporal queries and "+23.1 points" on multi-hop reasoning over its prior algorithm, at ~6,956 tokens per LoCoMo retrieval call.
- **Self-improving agent frameworks in the wild.** Nous's own `hermes-agent-self-evolution` repo (ICLR 2026 Oral, MIT) uses DSPy + GEPA to read execution traces and propose skill/prompt/code improvements behind constraint gates (tests, size limits, benchmarks) — an engineering instance of the learned-memory trend.

**The explicitly-named open problems** (from arXiv:2603.07670's closing section and the ICLR 2026 MemAgents workshop proposal): continual consolidation; causally-grounded retrieval; trustworthy reflection; **learned forgetting that doesn't delete safety-critical information**; multimodal/embodied memory; multi-agent memory synchronization and conflict resolution; interpretability of memory actions; and the cost of RL training over long horizons. A recurring caution: "long context is not memory" — bigger windows don't replace purpose-built memory.

## Recommendations

**If you're choosing or designing a memory architecture now:**

1. **Start with the simplest layer that works, then add.** Anthropic's own guidance is "do the simplest thing that works." Begin with (a) a curated instructions file (CLAUDE.md / MEMORY.md), (b) compaction at the window limit, and (c) just-in-time retrieval via file paths + grep before reaching for a vector DB or knowledge graph. Most teams over-engineer storage before they've nailed the write-path (what to remember) and retrieval relevance.
2. **Match the system to your control philosophy.** Choose **Claude Code-style** (harness-managed context + lightweight model notes) when you want a coding agent that stays lean and you'll curate CLAUDE.md by hand. Choose **Hermes-style** (agent-owned bounded memory + skills + session search) when you want an always-on personal agent that *accumulates competence* across weeks and you value never silently losing memory (its pre-compaction flush and FTS5 session search are the differentiators).
3. **Treat "what to remember" and "what to forget" as first-class.** Adopt explicit save/skip rules (Hermes) and bounded capacity that forces consolidation, rather than unbounded append. If you implement learned forgetting, add safety rails (Hermes's never-auto-delete + snapshots + pin/rollback is a good template).
4. **Protect against memory as an attack surface.** Given the May 2026 poisoning/exfiltration literature, scan memory writes (Hermes does), treat any externally-influenced content as untrusted before it enters persistent memory, and keep audit trails. This matters most for regulated workloads.
5. **Instrument before you optimize.** Run a `/context`-style breakdown of where tokens go (system prompt, tools, MCP schemas, memory files, messages). MCP tool schemas are a common hidden drain. KV-cache hit rate is the cost/latency metric to watch.

**Benchmarks/thresholds that should change your approach:**
- If recall degrades on long sessions → you have a context-rot problem (recall can drop 20–50% from 10k to 100k+ tokens per Chroma's data); compact earlier and offload to files, don't just buy a bigger window.
- If the agent re-explains/re-discovers the same things each session → invest in persistent semantic memory (MEMORY.md / `/memories`).
- If the agent repeats the same multi-step workflow → invest in procedural memory (skills) à la Hermes.
- If retrieval surfaces irrelevant memories → move from flat vector store toward graph/entity structure or reranking (the 2026 trend).
- If memory grows unbounded → add eviction/consolidation (capacity limits + a Curator-style pass).

## Caveats

- **Source quality varies.** Anthropic's engineering posts and the Hermes/Nous official docs and GitHub are primary and authoritative; many ecosystem details (compaction firing at "~95%", cost multipliers, GitHub star counts) come from reputable but secondary blogs and may drift. I've flagged primary vs. secondary where it matters.
- **A widely-repeated Hermes claim is unverified.** The "self-evaluation checkpoint every 15 tool calls" appears only in third-party blogs (origin appears to be hermes-agent.ai), not in any Nous Research primary source; Nous's own docs/GitHub describe an after-each-turn rubric-based review fork plus "periodic nudges" (no published interval) and a separate 7-day Curator cycle. The "5+ tool calls → skill creation" threshold *is* primary-sourced. Treat "15" as folklore.
- **Fast-moving arXiv preprints.** Many "where the field is going" papers (April–May 2026) are preprints, not peer-reviewed; their reported gains (ACE +10.6%, Mem0 +29.6/+23.1 points, FluxMem SOTA, etc.) are author-reported and benchmark-specific. Benchmark saturation and LLM-as-judge sensitivity are acknowledged problems, so treat single-number claims cautiously.
- **Version drift.** Both products iterate quickly. Specific token thresholds (Hermes 50%/85%; char limits 2,200/1,375; Curator 7-day/30-day/90-day) and Claude Code beta headers reflect the May 2026 docs and may change.
- **Scope.** I focused solution-specifics on Claude Code and Hermes and used Letta/MemGPT, Mem0, Manus, A-MEM, LangMem as comparative context, not exhaustive coverage of each.
