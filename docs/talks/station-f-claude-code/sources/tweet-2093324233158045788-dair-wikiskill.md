## Linked content summaries

**Paper — arXiv:2608.27454, "WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution"** (Tang et al., Google Research + Virginia Tech; v1 submitted 2026-08-27; fetched abs page + full HTML):

- **Problem**: agent skills (packaged knowledge/workflows — same concept as Claude Code skills) can be auto-discovered from agent experience, but the *insights* guiding skill development stay scattered across optimization histories and never get reused.
- **Architecture**: three separated layers — Trace Layer (raw execution experience), **Wiki Layer** (persistent structured knowledge), Skill Layer (evolving procedural skills). Loop of four components per iteration: Inference Agent (rollouts with current skills) → Wiki Maintainer (consolidates traces into the wiki) → Skill Proposer (uses wiki + traces to propose skill updates) → **Gating & Rollback** (keeps only updates that improve validation performance). Skills can be rolled back; the wiki always persists.
- **Eval**: five benchmarks — LiveMathematicanBench (math), SealQA (web search), SpreadSheetBench (spreadsheets), OfficeQA (long-context docQA), ALFWorld (embodied) — on five models from Qwen, Gemma, and Gemini families.
- **Key numbers** (from paper intro): within the Qwen family WikiSkill improves average performance by **+12.3% / +17.5% / +23.9%** for 4B/9B/27B — gains grow with model scale. Skills compensate for scale: **Qwen-3.5-9B with WikiSkill (47.4%) beats Qwen-3.6-27B without skills (39.4%)**.
- **Transfer**: evolved skills transfer across models and model families; skills evolved by *another* model can beat self-evolved skills.
- **Ablation**: persistent knowledge accumulation in the wiki is critical — matches dair_ai's summary. (Summary checked against the paper: all four claims in the tweet are accurate.)

## Relevance to the talk

- **Skills / self-improving skills** (core): academic validation of the exact practice Louis teaches — maintain a skill library, evolve it from experience. The paper's twist: don't stuff lessons into the skills themselves; keep a **separate persistent knowledge base** that skill updates draw from.
- **Memory / context engineering**: the Trace/Wiki/Skill separation is precisely the CLAUDE.md-vs-memory-files-vs-skills split in a Claude Code setup — raw transcripts ≠ distilled lessons (project memory / lessons.md) ≠ executable procedures (skills). Strong slide-ready mapping.
- **Evals**: the Gating & Rollback component = "no skill update ships without passing validation" — an evals-gate on self-improvement, directly analogous to keeping skill edits honest with eval suites (`claude plugin eval`).
- **Economic angle for founders**: smaller-model-with-evolved-skills beats bigger-model-without — accumulated organizational know-how is a cost lever (cheaper models + your skill library ≈ frontier-model performance on your tasks) and a moat (skills transfer across model families → not locked to one vendor).
